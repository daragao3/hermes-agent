pickle。已实现多种集合通信模式（例如 broadcast、all_gather 等），但它们大致都遵循以下流程：把输入对象转换为 pickle（原始字节），然后塞入一个字节张量；把该字节张量的大小告知各对端（第一次集合操作）；分配大小合适的张量以执行真正的集合通信；传输对象数据（第二次集合操作）；把原始数据转换回 Python（unpickle）。对象集合通信有时会表现出令人意外的性能或内存特性，导致运行时间过长或 OOM，因此使用时应当谨慎。以下是一些常见问题。pickle/unpickle 时间不对称 —— 视对象的数量、类型和大小而定，pickle 对象可能很慢。当集合通信存在扇入（例如 gather_object）时，接收方 rank 需要 unpickle 的对象数量是发送方 rank 需要 pickle 的 N 倍，这可能导致其他 rank 在其下一次集合通信中超时。张量通信效率低下 —— 张量应通过常规集合通信 API 发送，而不是对象集合通信 API。虽然可以通过对象集合通信 API 发送张量，但它们会被序列化和反序列化（对于非 CPU 张量还包括一次 CPU 同步和一次设备到主机的拷贝）；除了调试或排查问题的代码之外，几乎在所有情况下，都值得花功夫把代码重构为使用非对象集合通信。意外的张量设备 —— 如果你仍然想通过对象集合通信发送张量，还有一个特定于 cuda（可能也包括其他加速器）张量的方面需要注意。如果你 pickle 一个当前位于 cuda:3 上的张量，然后再 unpickle 它，你会得到另一个位于 cuda:3 上的张量，无论你身处哪个进程，也无论哪个 CUDA 设备是该进程的“默认”设备。而使用常规张量集合通信 API 时，“输出张量”始终位于同一个本地设备上，这通常才是你所期望的。如果这是该进程首次使用 GPU，unpickle 一个张量会隐式激活一个 CUDA 上下文，从而浪费大量 GPU 内存。把张量移到 CPU 之后再作为输入传给对象集合通信，即可避免这个问题。第三方后端# 除了内置的 **模式 8：** static_graph (bool) – 设为 True 时，DDP 知道训练图是静态的。静态图意味着：1）在整个训练循环中，已使用和未使用参数的集合不会改变；在这种情况下，用户是否设置 find_unused_parameters = True 无关紧要。2）图的训练方式在整个训练循环中不会改变（即不存在依赖迭代次数的控制流）。当 static_graph 设为 True 时，DDP 将支持以前无法支持的情况：1）可重入反向传播。2）多次激活检查点。3）模型有未使用参数时的激活检查点。4）存在前向函数之外的模型参数。5）当存在未使用参数时可能提升性能，因为 static_graph 设为 True 时 DDP 不会在每次迭代中搜索图以检测未使用参数。要检查是否可以将 static_graph 设为 True，一种方法是在之前的模型训练结束时检查 ddp 日志数据，如果 ddp_logging_data.get("can_set_static_graph") == True，大多数情况下也可以设置 static_graph = True。示例：>>> model_DDP = torch.nn.parallel.DistributedDataParallel(model) >>> # 训练循环 >>> ... >>> ddp_logging_data = model_DDP._get_ddp_logging_data() >>> static_graph = ddp_logging_data.get("can_set_static_graph")
